## Bug 15: `explained_variance` 计算导致 NaN

**问题描述**
训练过程中 `explained_variance` 日志输出为 `NaN`，导致 W&B 等监控显示异常。

**原因分析**
1. `loss_mask` 过滤掉 padding steps 后，剩余有效样本可能只有 1-4 个
2. `chunk_level` flatten 操作进一步消耗样本
3. `torch.var(unbiased=True)` 在样本数 < 2 时返回 NaN
4. 原代码未对 NaN/Inf 进行过滤，且 `ev_source` fallback 逻辑存在问题

**涉及文件**
- `rlinf/algorithms/losses.py` — `compute_ppo_critic_loss` 函数

**修复内容**

原始代码（line 346-382，原版本）：
```python
ev_source = "masked"
ev_returns = masked_returns
ev_values = masked_values
if valid_count < 2:
    ev_source = "unmasked_fallback"
    ev_returns = returns.reshape(-1)
    ev_values = values.reshape(-1)
    ...

var_returns_unbiased = torch.var(ev_returns)  # n<2时为NaN
var_returns = torch.var(ev_returns, unbiased=False)

if not torch.isnan(var_returns) and var_returns > var_eps:
    var_diff = torch.var(ev_returns - ev_values, unbiased=False)
    if not torch.isnan(var_diff):
        explained_variance = 1 - var_diff / var_returns
        ev_valid = True
    # 问题：else分支没有设置explained_variance，保持NaN
```

修复后代码：
```python
ev_returns = masked_returns
ev_values = masked_values
valid_mask = torch.isfinite(ev_returns) & torch.isfinite(ev_values)
ev_returns = ev_returns[valid_mask]
ev_values = ev_values[valid_mask]

var_eps = 1e-8
if ev_returns.numel() < 2:
    explained_variance = torch.tensor(0.0, device=returns.device)
    ev_valid = False
else:
    var_returns = torch.var(ev_returns, unbiased=False)

    if torch.isfinite(var_returns) and var_returns > var_eps:
        var_diff = torch.var(ev_returns - ev_values, unbiased=False)

        if torch.isfinite(var_diff):
            explained_variance = 1 - var_diff / var_returns
            ev_valid = True
        else:
            explained_variance = torch.tensor(0.0, device=returns.device)
            ev_valid = False
    else:
        explained_variance = torch.tensor(0.0, device=returns.device)
        ev_valid = False
```

**修复要点**
1. 新增 `torch.isfinite()` 过滤 NaN/Inf，避免传染
2. 统一使用 `biased` 方差（`unbiased=False`），样本少时更稳定
3. 所有失败分支明确返回 `0.0`，不再产生 NaN
4. 删除 `ev_source` fallback 到 unmasked 的无效逻辑

**metrics_data 变更**
```python
# 删除了这一行（ev_source已删除）
# "critic/explained_variance_source_masked": 1.0 if ev_source == "masked" else 0.0,
```

## Bug 17: 只走 base model hidden，不算 logits（不走 lm_head）

**问题描述**
PPO 的 value 分支只需要 hidden states；如果走到 logits/lm_head，会引入不必要的显存和计算开销，并干扰 value 路径排查。

**涉及文件**
- `omni_vla/src/openpi/models_pytorch/vlm_with_spatial.py`
- `rlinf/models/embodiment/openvla/openvla_action_model.py`
- `rlinf/models/embodiment/openvla_oft/rlinf/openvla_oft_action_model.py`

**关键实现**
1. `compute_values=True` 时强制 `output_hidden_states=True`，从 `hidden_states[-1]` 取特征进入 `value_head`。
2. 在 OmniVLA/VLM spatial 路径中，使用 `last_hidden_state` 或 `hidden_states[-1]` 继续后续计算，不依赖 `lm_head` logits。

**具体代码改动（按文件）**
1. `rlinf/models/embodiment/openvla/openvla_action_model.py`
   - `compute_values=True` 时设置 `output_hidden_states=True`（约 L544-L546）
   - value 分支从 `outputs.hidden_states[-1]` 取特征并进入 `value_head`（约 L593-L599）
   - logprobs 分支单独使用 `outputs.logits`，与 value 分支解耦（约 L564-L587）
2. `rlinf/models/embodiment/openvla_oft/rlinf/openvla_oft_action_model.py`
   - `compute_values=True` 时设置 `output_hidden_states=True`（约 L510-L512）
   - value 分支从 `outputs.hidden_states[-1]` 取特征并进入 `value_head`（约 L559-L565）
   - logprobs 分支单独使用 `outputs.logits`，与 value 分支解耦（约 L530-L553）
3. `omni_vla/src/openpi/models_pytorch/vlm_with_spatial.py`
   - reasoning 分支使用 `prefix_output.hidden_states[-1]`（约 L314-L324）
   - spatial/action 分支使用 `last_hidden_state`（约 L330-L355）
   - 以上路径均基于 base hidden states 继续计算，不依赖 `lm_head` 输出 logits。

**结论**
value/critic 路径按“base hidden-only”执行，符合 PPO 训练需求；该改动用于降低不必要开销并稳定训练排查。

## 2026-03-26 Proximal Anchor 结论与 Third-pass 计划

### 为什么增加冻结状态打印

需要确认两个编码器是否真的冻结，因此在 async actor 训练入口增加了低频日志，打印：

- `vggt_encoder`
- `vision_tower`

的 `training` 状态、`trainable_params` 和 `total_params`。

### 冻结状态日志结论

实测日志：

```text
vggt_encoder(training=True, frozen=True, trainable_params=0, total_params=248690120)
vision_tower(training=True, frozen=True, trainable_params=0, total_params=411955632)
```

结论：

- 两个编码器在参数层面确实已经冻结
- `trainable_params=0` 说明不会参与参数更新
- `training=True` 仅表示模块处于 train mode，不等价于“未冻结”
- 因此 frozen encoder 不是这次 `proximal_*` 退化的主因

### 为什么最初怀疑 proximal 仍有问题

在加 debug 之前，现象是：

- `pre_loss_logprob_prox_gap = 0`
- `proximal_ratio = 1`
- `proximal_approx_kl = 0`
- `clip_fraction = 0`

这组组合看起来像 `proximal_logprobs == current logprobs`，因此最初怀疑 proximal anchor 仍然在退化。

### Proximal anchor 修复后的新结论

修复为“上一版 actor 快照”后，debug 指标显示：

- `debug_pre_prox_old_gap_mean > 0`
- `debug_post_prox_old_gap_mean > 0`

这说明：

- `proximal_logprobs` 已经不再等于 `old_logprobs`
- proximal anchor 语义已经从 behavior policy 中分离出来
- 换言之，proximal anchor 的方向性修复是正确的

### 为什么修复后 `proximal_*` 仍然钉死

当前 async runner 的关键时序是：

1. `recv rollout`
2. `compute_proximal_logprobs`
3. `compute_advantages_and_returns`
4. `run_training(update_epoch=1)`
5. `optimizer_step`
6. `global_step += 1`
7. `sync rollout weights`

而当前 quickstart 配置为：

- `update_epoch = 1`
- `rollout_epoch = 1`

这意味着：

- `compute_proximal_logprobs()` 和训练前向发生在同一轮参数更新之前
- 本轮训练开始时，当前 actor 权重和 proximal snapshot 权重相同
- 真正的参数更新发生在本轮所有 micro-batch 之后

因此在当前配置下：

- `current logprobs == proximal logprobs`
- `proximal_ratio = 1`
- `proximal_approx_kl = 0`
- `clip_fraction = 0`

属于当前时序下的预期行为，不再作为 proximal 修复失败的证据。

### 当前主结论

截至这一轮：

- proximal anchor 语义已基本修正
- 真正未解决的主问题仍是 `train/actor/behav_approx_kl` 高，即 async lag
- `critic/explained_variance` 继续显著为负，说明 critic 解释力仍偏弱，且 value 有高估趋势
- 因此下一轮不再围绕 `proximal_*` 调参，而是直接限制 stale rollout

设计意图：

- 让 rollout 最多只领先 actor 一个版本窗口
- 减少明显过旧的数据继续进入训练
- 重点观察 `behav_approx_kl` 是否从当前 `40-60` 档位下降

第三轮主要验收指标：

## 2026-03-26 Fourth-pass：Actor 端 Keep-Latest Rollout Batch

### 为什么 third-pass 还不够

第三轮启用了：

- `algorithm.staleness_threshold = 0`

但后续结果显示：

- `train/actor/behav_approx_kl` 仍长期在 `30-60`
- `average_version` 与 `current_version` 几乎重合
- `env/rollout` 没明显回归，但 lag 也没有被真正压下去

结论是：

- `staleness_threshold=0` 只能阻止 rollout worker 继续超前生成
- 它不会清空 actor 输入通道里已经排队的旧轨迹
- actor 仍可能在训练 backlog 中较旧的完整 rollout batch

### Fourth-pass 策略

第四轮改为更强的 stale 控制：

- actor 在接收轨迹时，只保留最新的一个完整 rollout batch
- 若 replay channel 中已经积压了更多完整 batch，则按完整 batch 为单位把更旧数据全部读掉并丢弃
- 不按单条 trajectory 随机丢弃，不改 batch 内部组成

### 新增观测指标

为了确认 stale backlog 是否真的被切掉，训练侧新增：

- `train/actor/received_rollout_version_max`
- `train/actor/received_rollout_version_gap`
- `train/actor/current_version_minus_batch_version_max`

### Fourth-pass 验收重点

## 2026-03-26 Fifth-pass：修正 Rollout 的已应用权重版本口径

### Fourth-pass 暴露出的新问题

第四轮加入 actor 端 keep-latest batch 之后，新增指标显示：

- `replay_channel_qsize_before_recv = 0`
- `replay_channel_qsize_after_drain = 0`
- `dropped_rollout_chunks = 0`
- `dropped_rollout_batches = 0`

结论：

- actor 通道 backlog 不是主因
- keep-latest 策略没有真正触发

但同时：

- `received_rollout_version_min = received_rollout_version_max`
- `current_version_minus_batch_version_max = 1`
- `behav_approx_kl` 仍长期在 `35-65`

这提示现有 `versions` 口径可能低估了真实 stale 程度。

### 根因定位

代码检查发现：

- rollout worker 的 `set_global_step()` 会直接更新 `self.version`
- rollout 结果里的 `versions` 直接写的是 `self.version`
- 但这不等于 rollout 模型已经真正完成 `load_state_dict()`

因此之前的 `versions` 更接近 runner 写入的逻辑步数，而不是 rollout 实际用于生成这批数据的已应用权重版本。

### Fifth-pass 改动

第五轮改为显式区分两类版本：

- `version`：runner logical version
- `applied_weight_version`：rollout worker 真正已经 load 到模型上的权重版本

同步改动包括：

- actor->rollout 的权重同步 payload 里显式携带 `weight_version`
- rollout 只有在 `load_state_dict()` 完成后才刷新 `applied_weight_version`
- rollout 生成结果里的 `versions` 改为写入 `applied_weight_version`

### 新增观测指标

为了判断 rollout 权重同步是否真正落后，新增：

- `rollout/applied_weight_version`
- `rollout/requested_weight_version`
- `rollout/applied_minus_runner_version`
- `rollout/weight_sync_apply_total`
- `rollout/weight_sync_request_total`
- `rollout/weight_sync_coalesced_total`

第五轮重点不再先改超参，而是先让 lag 度量变得可信，再决定下一步是改同步时序还是改 actor 单步更新强度。

### 第五轮实现后的 OOM 与收敛处理

第一次把 `weight_version` 和 `state_dict` 一起作为同步 payload 传输后，训练在
`AsyncMultiStepRolloutWorker.sync_model_from_actor` 阶段触发了 Ray OOM：

- rollout 同步 worker 内存峰值约 `36GB`
- 节点总内存占用逼近 Ray kill threshold，worker 被系统回收
- 后续出现的 `EGL_NOT_INITIALIZED` 属于 env worker 被连带杀掉后的清理噪声，不是主因

因此同步实现收敛到更省内存的版本：

- actor->rollout 再次只传裸 `state_dict`
- rollout 在 `load_state_dict()` 真正完成后，把 `applied_weight_version` 记录为当前 `self.version`

这个版本没有精确到“额外显式传一个独立权重版本号”，但在当前 runner 时序下：

1. `rollout.set_global_step(step)`
2. `sync_model_from_actor()`

顺序固定，因此它仍然比旧版“在生成时直接读 `self.version`”更可靠，同时避免了 payload 包装导致的额外内存峰值。

## 2026-03-27 代码排查：怀疑 rollout / actor 前向语义不一致

### 排查动机

在行为权重诊断不能解释高 `behav_approx_kl` 之后，开始怀疑问题不完全是超参，而可能有实现口径差异。

重点关注到：

- rollout worker 默认使用 `model.eval()`
- actor 侧重算 `proximal_logprobs` 时，历史上默认使用 `model.train()`
- Omni-VLA 的 PPO logprob 路径对 `self.training` 明显敏感

### 关键发现

代码回溯发现：

1. `critic` 走 hidden-only、不过 `lm_head/logits` 的改动本身更像是显存优化，而不是当前高 `behav_approx_kl` 的主因
2. 真正更可疑的是那次显存优化同时引入了依赖 `self.training` 的两套前向语义：
   - 训练态下 `prefix / middle` 会强制 `no_grad`
   - 训练态与评估态对 suffix 的 `past_key_values` 处理也不同
3. 因此更像是：
   - rollout 产出的 `old_logprobs` 来自 eval 语义
   - actor 侧的 `proximal/current` 来自 train 语义
   - 最终把 `behav_approx_kl` 和 `prox_old_gap` 人为放大

### 实验改动

为验证这一点，增加：

- `algorithm.proximal_recompute_model_mode`

支持：

- `train`
- `eval`

用于控制 actor 侧重算 `proximal_logprobs` 时的 model mode。

## 2026-03-27 Twelfth-pass 尝试：`proximal_recompute_model_mode = eval`

### 改动

本轮尝试将：

- `algorithm.proximal_recompute_model_mode: train -> eval`

目的：

- 让 actor 侧重算 `proximal_logprobs` 时尽量贴近 rollout 的 eval 语义
- 验证高 `behav_approx_kl` 是否主要来自 train / eval 前向不匹配

### 结果

该实验未能完成，actor 在 `compute_proximal_logprobs()` 阶段触发 OOM：

- `torch.OutOfMemoryError: Tried to allocate 10.63 GiB`
- 后续由于 forward 尚未正常退出，`cpu_weight_swap` 回滚权重时又触发
  `AssertionError: Expects the handle training to be IDLE but got HandleTrainingState.FORWARD`

### 结论

这说明：

- 不能简单通过全局 `self.model.eval()` 来验证 rollout / actor 语义差异
- 因为 Omni-VLA 前向中多处逻辑直接依赖 `self.training`
- 切到 eval 不只是改变“行为语义”，还会把训练态下的省显存路径一并关掉
- 结果是 proximal 重算走到了更重的前向分支，从而在 actor 侧 OOM

因此，这次失败并不否定“train / eval 前向不一致”这个怀疑；相反，它进一步说明 Omni-VLA 当前实现里，`self.training` 同时混合了承载：

- 行为语义
- 显存优化策略
- cache 处理策略

这三者不应被简单绑在一起切换。

### 回退

为恢复可运行基线，已将配置回退为：

- `algorithm.proximal_recompute_model_mode: train`
