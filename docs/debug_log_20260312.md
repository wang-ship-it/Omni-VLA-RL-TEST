## Bug 8: attention mask dtype 与 query dtype 不匹配

**报错**
```
RuntimeError: invalid dtype for bias - should match query's dtype
```

**位置**
`omni_vla/src/openpi/models_pytorch/vlm_with_spatial.py:328`，在 `spatial_expert.forward()` 内部的 SDPA 调用

**原因**
`_prepare_attention_masks_4d` 生成的 mask 是 **float32**（Python float 字面量默认 float32）。`reasoning_expert` 使用项目自定义的 `transformers_replace` 实现，对 mask dtype 宽松；而 `spatial_expert` / `action_expert` 使用 HF 官方 `GemmaForCausalLM`，SDPA 严格要求 mask dtype 与 query dtype（bfloat16）一致。

**修复**
在调用 `spatial_expert` 和 `action_expert` 前，将 attention mask 转换为对应模型参数的 dtype：
```python
# vlm_with_spatial.py - spatial_expert 调用处
spatial_dtype = next(self.spatial_expert.parameters()).dtype
spatial_attention_mask = attention_mask.to(dtype=spatial_dtype) if attention_mask is not None else None
middle_output = self.spatial_expert.forward(
    inputs_embeds=inputs_embeds[1],
    attention_mask=spatial_attention_mask,
    ...
)

# vlm_with_spatial.py - action_expert 调用处
action_dtype = next(self.action_expert.parameters()).dtype
action_attention_mask = attention_mask.to(dtype=action_dtype) if attention_mask is not None else None
suffix_output = self.action_expert.forward(
    inputs_embeds=inputs_embeds[2],
    attention_mask=action_attention_mask,
    ...
)
```

## Bug 9: FSDP `full_shard` 反向传播 storage 为零

**报错**
```
RuntimeError: setStorage: sizes [256, 1024], strides [1024, 1], storage offset 2359296,
and itemsize 2 requiring a storage size of 5242880 are out of bounds for storage of size 0
```

**位置**
`rlinf/workers/actor/fsdp_actor_worker.py:1443`，`loss.backward()` 时

**原因**
FSDP `full_shard` 在前向传播后会 reshard（释放）参数的 storage。对于冻结参数（`requires_grad=False`），反向传播时 FSDP 不会重新 all-gather（因为不需要梯度），但某些中间计算仍需访问这些参数，导致 "storage of size 0" 错误。这是 PyTorch FSDP v1 在混合冻结/可训练参数场景下的已知问题。

**修复**
将 `sharding_strategy` 从 `full_shard` 改为 `no_shard`（与项目中 `libero_spatial_dsrl_openpi.yaml` 的做法一致）：
```yaml
fsdp_config:
  sharding_strategy: "no_shard"  # 原来是 "full_shard"
```

**代价**
`no_shard` 等价于 DDP，每卡保留完整模型副本，显存占用更高，且无法通过参数切分利用多卡并行。

## 显存占用对比分析：OmniVLA vs Pi0（OpenPi）

### 配置对比

| 配置项 | Pi0 (`libero_spatial_ppo_openpi`) | OmniVLA (`quickstart`) |
|---|---|---|
| 模型 | `model/pi0` | `model/omni_vla` |
| `micro_batch_size` | 128 | 8（原 16，因 OOM 降低） |
| `global_batch_size` | 2048 | 384 |
| `total_num_envs` (train) | 32 | 8 |
| `rollout_epoch` | 16 | 2 |
| `sharding_strategy` | `no_shard` | `no_shard`（原 `full_shard`，因 Bug 9 改） |
| `gradient_checkpointing` | False | False |

### 模型架构对比

#### Pi0（OpenPi）— 2 个子模型

| 组件 | 架构 | 参数量 | bf16 显存 |
|---|---|---|---|
| PaliGemma VLM | SigLIP ViT + Gemma-2B (18层, width=2048, mlp=16384) | ~3B | ~6 GB |
| Action Expert | Gemma-300M (18层, width=1024, mlp=4096) | ~311M | ~0.6 GB |
| **合计** | | **~3.3B** | **~6.6 GB** |

#### OmniVLA — 4 个子模型

| 组件 | 架构 | 参数量 | bf16 显存 |
|---|---|---|---|
| PaliGemma VLM (reasoning_expert) | SigLIP ViT + Gemma-2B (18层, width=2048, mlp=16384) | ~3B | ~6 GB |
| **Spatial Expert (新增)** | **GemmaForCausalLM (18层, width=1024, mlp=4096)** | **~311M** | **~0.6 GB** |
| Action Expert | Gemma-300M (18层, width=1024, mlp=4096) | ~311M | ~0.6 GB |
| **VGGT Encoder (新增)** | **VGGT-1B (ViT Aggregator, embed_dim=1024)** | **~1B** | **~2 GB** |
| **合计** | | **~4.6B** | **~9.2 GB** |

### 显存构成分析（单卡，no_shard 模式）

| 显存组成 | Pi0 (~40 GB) | OmniVLA (~75 GB) | 增量原因 |
|---|---|---|---|
| 模型权重 (bf16) | ~6.6 GB | ~9.2 GB | +VGGT(2GB) +Spatial(0.6GB) |
| Rollout 模型副本 | ~6.6 GB | ~9.2 GB | 同上，推理用完整副本 |
| 优化器状态 (fp32) | ~13.2 GB (仅可训练部分) | ~18.4 GB (更多可训练参数) | Adam 需 2× 参数量的 fp32 状态 |
| 梯度 (bf16) | ~6.6 GB | ~9.2 GB | |
| 前向激活值 | ~5-7 GB | ~25-30 GB | **主要增量来源** |
| PyTorch 碎片/缓存 | ~2 GB | ~2 GB | |

### 关键差异分析

**1. 模型本身多了约 1.3B 参数（+2.6 GB 权重）**

OmniVLA 相比 Pi0 多了：
- VGGT-1B Encoder (~1B params)：用于空间几何理解
- Spatial Expert (~311M params)：独立的空间推理 Gemma 模型

这部分权重 × 2（Actor + Rollout 各一份）= 额外约 **5.2 GB**。

**2. 前向激活值是最大增量（+18-23 GB）**

OmniVLA 的前向传播涉及 4 个子模型的串联/并联计算：
- VGGT 对图像做特征提取（1B 模型处理 256×256 图像，特征图很大）
- Reasoning Expert、Spatial Expert、Action Expert 三个 Transformer 通过共享注意力机制联合前向
- 中间有 `spatial_to_reasoning` 投影层和多次 attention mask 计算
- 所有激活都需保留用于反向传播（`gradient_checkpointing=False`）

Pi0 只有 PaliGemma + Action Expert 两个模型的前向，计算图简单得多。

**3. 优化器状态增加**

OmniVLA 可训练参数更多，Adam 的 momentum 和 variance 都是 fp32 存储，额外约 **5 GB**。

### 优化建议（按效果排序）

1. **开启 gradient_checkpointing**：节省 60%+ 激活显存（约省 15-18 GB），代价是训练速度降低 ~20-30%
2. **开启 rollout enable_offload**：推理完后将 rollout 模型权重移到 CPU，释放约 9 GB
3. **冻结 VGGT + Spatial Expert**：减少优化器状态，但需评估是否影响训练效果
4. **减少 `total_num_envs`**：降低 rollout 轨迹存储
5. **尝试 `shard_grad_op`**：切分梯度和优化器状态（不 reshard 参数，避免 Bug 9），预计省 5-10 GB

## Bug 10: SFT checkpoint 权重 key 不匹配导致 reasoning_expert 未加载（根因）

**现象**
- `env/reward=0.0`, `env/success_once=0.0` 贯穿所有训练步
- `critic/explained_variance` 深度负值（-10 到 -60）
- `rollout/advantages_mean` ≈ 1e-8（几乎为零）

**位置**
`rlinf/models/embodiment/omni_vla/__init__.py:73`

**原因**
`safetensors.torch.load_model(model, weight_path, strict=False)` 使用 `strict=False` 加载 SFT checkpoint，但 checkpoint 的 key 层级与模型 state_dict 的 key 层级不匹配，导致 **613 个 key 静默跳过**。

具体差异（以 reasoning_expert 的 language_model 为例）：
```
checkpoint key: reasoning_spatial_expert.reasoning_expert.language_model.model.layers.X...
model key:      reasoning_spatial_expert.reasoning_expert.model.language_model.layers.X...
```

`.model.` 的位置不同——checkpoint 保存时 PaliGemma 的结构是 `reasoning_expert.language_model.model.layers`，但 HuggingFace 的 `PaliGemmaForConditionalGeneration` 的 state_dict 层级是 `reasoning_expert.model.language_model.layers`。

同样的 mismatch 也影响 `vision_tower` 和 `multi_modal_projector`：
```
checkpoint: reasoning_expert.vision_tower.X
model:      reasoning_expert.model.vision_tower.X
```

**结果**
reasoning_expert（PaliGemma）的所有权重——语言模型、视觉编码器、多模态投影器——**全部没有从 SFT checkpoint 加载**，仍然是 `VLMWithSpatialActionExpertModel.__init__` 中加载的原始 pretrained 权重。模型对 LIBERO 任务的理解完全错误，输出无意义的动作。

**修复**
在权重加载时添加 key remapping 逻辑：
```python
def _remap_ckpt_key(key: str) -> str:
    prefix = "reasoning_spatial_expert.reasoning_expert."
    if key.startswith(prefix):
        suffix = key[len(prefix):]
        if suffix.startswith("language_model.model."):
            return prefix + "model.language_model." + suffix[len("language_model.model."):]
        if suffix.startswith("language_model.lm_head."):
            return prefix + suffix[len("language_model."):]
        if suffix.startswith("vision_tower."):
            return prefix + "model." + suffix
        if suffix.startswith("multi_modal_projector."):
            return prefix + "model." + suffix
    return key
```

同时处理 PaliGemma 的权重绑定（embed_tokens 与 lm_head 共享权重）：
```python
lm_head_key = "reasoning_spatial_expert.reasoning_expert.lm_head.weight"
embed_tokens_key = "reasoning_spatial_expert.reasoning_expert.model.language_model.embed_tokens.weight"
if lm_head_key in remapped_state_dict and embed_tokens_key not in remapped_state_dict:
    remapped_state_dict[embed_tokens_key] = remapped_state_dict[lm_head_key]
```

**修复后**
missing keys 从 613 降至 9（均为预期 missing：8 个 value_head + 1 个 spatial_expert.embed_tokens）。
`env/success_once` 从 0.0 恢复至 **0.875**（16 个 trajectory 中 14 个成功）。

## Bug 11: `embed_spatial` 图像双重归一化

**位置**
`omni_vla/src/openpi/models_pytorch/omni_vla.py:369`

```python
images_flat = F.interpolate(images_flat, size=(252, 252), mode="bilinear", align_corners=False)
# images are already in [-1, 1] from Observation.from_dict, no need to rescale
```

## Bug 13: Critic loss shape mismatch（`explained_variance = -2`）

**现象**
`train/critic/explained_variance` 训练全程卡在 **-2**，value function 完全无法预测 return。
`rollout/advantages_mean` 持续向负方向漂移（-0.8 → -1.4）。

**位置**
`rlinf/models/embodiment/omni_vla/omni_vla_action_model.py`，`default_forward()` 第 307 行

**原因**
Shape mismatch 导致 PyTorch silent broadcasting 错误：

- Rollout 中 `prev_values`：`sample_actions()` 用 `keepdim=True` 返回 `[bsize, 1]`
- `reward_type=chunk_level` 预处理后 `returns`、`prev_values` 均为 `[N, 1]`
- 但 training 时 `default_forward()` 用 `keepdim=False` 返回 `values = [N]`

在 `compute_ppo_critic_loss()` 中：
```python
values - prev_values  →  [N] - [N,1]  →  [N, N]  # 叉积，完全错误！
returns - values      →  [N,1] - [N]  →  [N, N]  # 同样错误
```
Critic loss 在 `[N, N]` 矩阵上计算，value head 收到完全错误的梯度信号，导致 `explained_variance` 卡在 -2。

**修复**
```python
# 修改前（omni_vla_action_model.py:307）
value_t = value_t.mean(dim=-1, keepdim=False)  # [bsize]

# 修改后
value_t = value_t.mean(dim=-1, keepdim=True)   # [bsize, 1]
```

## Bug 14: `rollout/advantages_mean` 指标包含无效 padding step

**现象**
`rollout/advantages_mean` 在 `normalize_advantages=True` 时仍持续显示 -0.8 到 -1.4，理论上归一化后均值应接近 0。

**位置**
`rlinf/utils/metric_utils.py`，`compute_rollout_metrics()` 函数

**原因**
`safe_normalize()` 只对 `loss_mask=True` 的有效步骤计算 mean/std，但也对无效步骤（episode 结束后的 padding）执行了归一化（减 valid_mean，除 valid_std）。
无效步骤的 advantage 原始值为负（≈ 0 - value_old ≈ -1.0），归一化后仍为负值。
`compute_rollout_metrics()` 用 `torch.mean(advantages)` 对全部元素（含无效步骤）取均值，导致指标被拉偏。

**修复**
在 advantages 和 returns 两个统计 block 中均添加 `loss_mask` 过滤：
```python
loss_mask = data_buffer.get("loss_mask", None)

# advantages block
if loss_mask is not None:
    valid_adv = advantages[loss_mask]
    mean_adv = valid_adv.mean().to(torch.cuda.current_device())
    max_adv = valid_adv.max().detach().item()
    min_adv = valid_adv.min().detach().item()
else:
    mean_adv = torch.mean(advantages).to(torch.cuda.current_device())
    max_adv = torch.max(advantages).detach().item()
    min_adv = torch.min(advantages).detach().item()
# returns block 同理
```
